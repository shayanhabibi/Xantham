## Step 2: mechanism, fully explained - not a CLI code defect

`src/Xantham.Cli/Program.fs`'s `emit` calls `Pipeline.run config packageDir outDir`, and
`Pipeline.run` (`src/Xantham.Generator/Pipeline.fs`) is a thin wrapper: it calls
`Pipeline.generate` unchanged, then writes `generate`'s files to disk. There is no separate
option, default, or pass-list the CLI applies - `Pipeline.generate` is the one function both the
CLI and every test in `Pipeline.test.fs` call. `Program.fs`'s own `loadConfig` is exactly
`GeneratorConfig.load packageDir` (or `GeneratorConfig.loadFile`/`GeneratorConfig.load` under
`--config`), which is the same call `Cli.test.fs`'s `matchesPipeline` uses to prove the CLI
byte-identical to `Pipeline.generate` for `lab` and `group-map-lab`.

The divergence is entirely in **which `GeneratorConfig` each caller supplies** for this one
fixture:

- `Pipeline.test.fs:2658` builds `workersTypesConfig = { GeneratorConfig.Default with Lib = Some
  [ "esnext" ] }` **directly in F# and hands it straight to `Pipeline.generate`** - it never goes
  through `GeneratorConfig.load`, so no file backs it.
- The CLI has only `GeneratorConfig.load packageDir`, which reads `<packageDir>/xantham.json`.
  No such file exists inside the installed `@cloudflare/workers-types` package, and none can be
  committed there: `.gitignore` line 29 (`tests/fixtures/**/*`) excludes everything under
  `tests/fixtures/` except the `*lab` family and `pins.json` (lines 41-56), and the npm rung's own
  directory is regenerated by `npm install` regardless.

Proof this is a config difference, not a code path difference: pointing the CLI at an ordinary,
loadable config with the same override reproduces the golden byte for byte.

```
echo '{ "lib": ["esnext"] }' > /tmp/xantham-ci-cfg/xantham.json
dotnet run --project src/Xantham.Cli -- generate <package> --config /tmp/xantham-ci-cfg -o out
diff out/Cloudflare.WorkersTypes.fs tests/Xantham.Generator.Tests/golden/@cloudflare/workers-types/Cloudflare.WorkersTypes.fs
# no output - byte identical, 30,235 lines both sides
```

Without `Lib = ["esnext"]`, the DOM lib loads and ~154 of workers-types' own classes that share a
name with `lib.dom.d.ts` (`Headers`, `Response`, `Event`, `Crypto`, ...) merge into the DOM
declaration at harvest and never reach workers-types' own binding - that is where the missing
~4,300 lines go. `Pipeline.test.fs`'s own comment at the config site says this: the override
exists because the package's README prescribes `"lib": ["esnext"]` for exactly this reason, and
"the rung runs the way a consumer would" - i.e. the intended real-world caller is a consumer
project that carries its own `xantham.json` with that override beside its own `package.json`,
not a bare invocation over the untracked npm-installed fixture directory.

## Why this is not fixed here

Wave thirteen's measurement compared the CLI's default-config run against a config that exists
nowhere on disk this repository can commit to - not a CLI omission of an option, default or pass.
Closing it would mean one of:

- Baking `@cloudflare/workers-types`-specific defaults into `GeneratorConfig.Default` or
  `Bootstrap.fs`, which changes the default library set for every fixture and every consumer,
  not just this one package - reshaping the pipeline, out of scope per the brief.
- Loosening `.gitignore`'s `tests/fixtures/**/*` policy to carry a config file inside an
  npm-installed, reinstallable directory - not owned by this lane, and contrary to the fixtures
  rule's tracked/untracked split (`pins.json` is the only tracked record for npm rungs).

Neither is a contained change to `src/Xantham.Cli/` or `Pipeline.fs`. No code change made.
